# Руководство для агентов

## Дизайн

- Дизайн проекта доступен в Figma: https://www.figma.com/design/Msacz6Yb1HAj6xqmb82aPD/Untitled?node-id=0-1&p=f&t=GQgBztZd9CmCJfbQ-0. Он доступен через подключённую интеграцию Figma.

На страницах флоу авторизации не делай svg для дизайна, а оставь плейсхолдер для изображения.

## Стек и подход

- Используй Vue 3, Composition API и JavaScript. Новые компоненты пиши через `<script setup>`.
- Не добавляй TypeScript и не выполняй несвязанные миграции или рефакторинги.
- Даже если Figma предлагает React, Tailwind или Code Connect snippets, используй их только как визуальную справку. Не добавляй React, Tailwind, JSX или utility-классы Tailwind.
- Предпочитай single-file components: компонент, его шаблон, логика и локальные стили должны находиться в одном `.vue`-файле. Выноси стили в отдельный файл только если они крупные или переиспользуются.

## Именование

- Имена должны быть на английском, отражать логическое назначение и оставаться компактными. Не используй неясные сокращения, однобуквенные имена и чрезмерно длинные конструкции.
- Переменные и функции именуй в `camelCase`.
- Vue-компоненты и их файлы именуй в `PascalCase` (`UserProfile.vue`).
- Остальные файлы, директории и CSS-классы именуй в `kebab-case` (`user-profile`).

## Архитектура

- Организуй приложение по Feature-Sliced Design (FSD): `app`, `pages`, `widgets`, `features`, `entities`, `shared`.
- Создавай слои и слайсы только когда они нужны; не создавай пустые каталоги ради формальной структуры.
- Направление зависимостей — только вниз: `pages` могут использовать `widgets`, `features`, `entities`, `shared`; `widgets` — `features`, `entities`, `shared`; `features` — `entities`, `shared`; `entities` — `shared`.
- Не импортируй код между слайсами одного слоя напрямую. Внешнее использование слайса допускается только через его публичный API — `index.js`.
- Существующий код переносится в FSD только при работе с ним или если этого требует задача. Не выполняй массовую миграцию без отдельного запроса.

## Стили

- Пиши стили на indented Sass: используй расширение `.sass` и `<style lang="sass">`; не используй SCSS.
- Если Sass ещё не настроен, добавь пакет `sass` в `devDependencies` до первого изменения со стилями Sass.
- Для локальных стилей компонентов используй `<style scoped lang="sass">`.
- Глобальные стили размещай только в `src/app/styles`.
- SVG-иконки храни в каталоге `assets` соответствующего FSD-слайса; общие иконки — в `src/shared/assets`.
- CSS-классы оформляй по БЭМ: `block`, `block__element`, `block--modifier`.
- Не используй глубоко вложенные селекторы; Sass-вложенность должна отражать БЭМ-структуру и оставаться небольшой.

## Проверка изменений

- После изменений кода, стилей или конфигурации выполни `npm run lint` и `npm run build`.
- Сообщи, если проверку невозможно выполнить или она завершилась ошибкой.

## Предметная область и этапы

- Dionysus превращает аудио- или видеозапись встречи в проект с транскрипцией и структурированным ТЗ. Подробные требования из `../Кейс 3. Томск.pdf` относятся преимущественно к странице ТЗ; до отдельной задачи эта страница остаётся заглушкой.
- Разрабатывай в два этапа: сначала все согласованные интерфейсы на локальных контрактных данных, затем подключай реальный API. Не смешивай оба этапа в одной задаче без отдельного запроса.
- В первом этапе реализуй все экраны из Figma, кроме полноценного редактора ТЗ: лендинг, регистрацию, вход, подтверждение email, восстановление пароля, проекты, поиск, создание проекта и профиль.
- На каждом асинхронном или зависящем от данных экране предусмотри загрузку, пустой результат, ошибку и успешное состояние, если они применимы.

## Контракты backend

- Перед интеграцией сверяй контракты с backend-кодом. Не проектируй UI вокруг полей, статусов или возможностей, которых сервер фактически не предоставляет.
- Аутентификация использует access token из ответа и HttpOnly refresh cookie. Запросы с обновлением токена должны отправлять credentials; защищённые запросы — Bearer access token.
- Пароль: не менее 8 символов, минимум одна цифра и одна заглавная буква.
- Для создания проекта отправляй `multipart/form-data` с полями `name` и `media`, только аудио/видео, максимум 100 МБ. Не используй устаревшие имена `title` и `file` из тестов backend.
- Текущий `POST /api/projects` обрабатывается синхронно: успешный ответ возвращает созданный проект, ошибки конвертации и транскрибации — соответственно 422 и 502. Не создавай клиентский polling без появления соответствующего server-контракта.
- Список проектов содержит `id`, `name`, `createdAt`, `status`; детали проекта содержат записи и сегменты транскрипции с `startSeconds`, `endSeconds`, `text`. Поиск проектов и транскрипции требует запрос длиной не менее двух символов.
- Для сохранения изменений профиля не подтверждён backend-контракт. До появления endpoint не отправляй вымышленные запросы и честно оставляй форму локальным UI-состоянием.
- Локальный backend доступен по `http://localhost:8000`; перед изменением интеграции сверяй Swagger на `http://localhost:8000/swagger/index.html` и доступность через `GET /health`.
- Whisper запущен по `http://localhost:9000` как внутренняя backend-зависимость. Frontend не обращается к нему напрямую.
